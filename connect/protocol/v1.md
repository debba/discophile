# Discophile Connect protocol, version 1

Status: draft for review. Version 1 covers instance discovery, native sign-in, the account, and plan entitlements. Device pairing, encrypted synchronization, and playback handoff are not part of version 1 and will be added as separate capabilities after their own specifications are reviewed.

This document is self-contained. It describes what a client such as Discophile for computers or Discophile for iPhone expects from any compatible server, and what such a server must do. It does not depend on the official service's database, identity provider, or hosting.

The key words "must", "must not", "should", and "may" are used as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

## Overview

A Connect instance is identified by its canonical origin: the scheme, lowercase host, and port of its base URL, with the default port omitted and no trailing slash, such as `https://connect.example.org`. The official instance is `https://connect.discophile.app`. Clients let people choose another instance; every token, identifier, and cached value belongs to exactly one origin.

A client:

1. Reads the instance's discovery document and checks that it describes the same origin.
2. Signs the person in through the system browser with OAuth 2.0 authorization code and PKCE.
3. Reads the account and its plan with the access token.
4. Revokes its delegation when the person signs out or changes instance.

Every URL a client receives from an instance must have the instance's origin. A client must reject a document that points authorization, tokens, or resources to another origin, and must not follow HTTP redirects on requests that carry credentials or tokens.

## Transport

- Instances must use HTTPS with a certificate valid for their host. Clients must not offer a general option to disable certificate verification.
- As an explicit development exception, clients may accept `http` for the loopback hosts `localhost`, `127.0.0.1`, and `[::1]`, and must show that the connection is not encrypted.
- Request and response bodies are UTF-8 JSON, except the OAuth token and revocation endpoints, which accept `application/x-www-form-urlencoded` as required by OAuth.
- Clients should send `Accept: application/json` and a `User-Agent` identifying the app and its version.
- Servers must send `Cache-Control: no-store` on responses that contain tokens or account data.
- Timestamps are RFC 3339 strings in UTC, such as `2027-01-31T00:00:00Z`. They may include fractional seconds, such as `2027-01-31T00:00:00.000Z`.
- Clients must ignore unknown JSON members. Servers must ignore unknown query parameters except where this document requires an error.

## Discovery

`GET /api/v1/server-info` is public and requires no authentication.

```json
{
  "protocol": "discophile-connect",
  "protocolVersions": [1],
  "instance": {
    "id": "9b0d0c5e-7f1e-4c39-9d0e-2f3a2c1b5e77",
    "origin": "https://connect.discophile.app",
    "name": "Discophile Connect"
  },
  "authorization": {
    "issuer": "https://connect.discophile.app",
    "authorizationEndpoint": "https://connect.discophile.app/oauth/authorize",
    "tokenEndpoint": "https://connect.discophile.app/oauth/token",
    "revocationEndpoint": "https://connect.discophile.app/oauth/revoke",
    "scopesSupported": ["account:read", "offline_access"],
    "nativeClients": ["discophile-desktop", "discophile-android", "discophile-ios"]
  },
  "resources": {
    "api": "https://connect.discophile.app/api/v1"
  },
  "capabilities": {
    "account": { "version": 1 }
  },
  "links": {
    "dashboard": "https://connect.discophile.app/account"
  }
}
```

| Member | Required | Meaning |
| --- | --- | --- |
| `protocol` | yes | Always `discophile-connect`. |
| `protocolVersions` | yes | Protocol versions the instance implements. A version 1 client requires `1`. |
| `instance.id` | yes | A stable identifier chosen by the instance, at most 128 characters. It must not change while the instance keeps its accounts. A client that sees a different identifier at the same origin treats it as a different instance: it deletes its tokens, revokes them on a best-effort basis, and asks the person to sign in again. |
| `instance.origin` | yes | The canonical origin. It must equal the origin the client used to reach the document. |
| `instance.name` | no | A display name, at most 100 characters. Clients show the origin as well, never the name alone. |
| `authorization.issuer` | yes | The OAuth issuer. In version 1 it must equal `instance.origin`. |
| `authorization.*Endpoint` | yes | Absolute URLs with the instance's origin. |
| `authorization.scopesSupported` | yes | Must include `account:read` and `offline_access`. |
| `authorization.nativeClients` | yes | The [native client identifiers](#native-clients) the instance accepts. |
| `resources.api` | yes | The resource indicator for this API, `<origin>/api/v1`. |
| `capabilities` | yes | Features the instance offers now, keyed by name, each with the version implemented. |
| `links.dashboard` | no | A page where the person manages their account in a browser, with the instance's origin. Clients ignore a link to another origin. |

Endpoints and resources are absolute URLs without a query or fragment. The client must reject the document when `protocol` differs, `protocolVersions` lacks a version it implements, `instance.origin` or `authorization.issuer` differs from the origin it used, any endpoint or resource has another origin or a query or fragment, or `resources.api` is not `<origin>/api/v1`.

### Capabilities

Version 1 defines one capability:

- `account`, version 1: `GET /api/v1/account` as described below.

A capability's version only grows with additions that older clients can ignore, so a client uses a capability whose advertised version is at least the one it implements. An incompatible change uses a new capability name or a new protocol version.

The names `devices`, `sync`, `backup`, `remote`, and `handoff` are defined by the optional [native services extension](services.md). Clients must ignore unknown capabilities, must not call endpoints of a capability the instance does not advertise, and must not infer a capability from the person's plan. An instance that offers accounts and plans but no synchronization is fully compliant with version 1.

Instances should also publish OAuth authorization server metadata at `/.well-known/oauth-authorization-server` ([RFC 8414](https://www.rfc-editor.org/rfc/rfc8414)) with the same issuer and endpoints. Clients may rely on `server-info` alone.

## Native sign-in

Native sign-in follows [OAuth 2.0 for Native Apps](https://www.rfc-editor.org/rfc/rfc8252): the authorization code grant with PKCE ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)), opened in the system browser or the platform's authentication session, never in an embedded web view that the app can inspect.

How the instance identifies the person (social providers, passwords, passkeys, or anything else) is its own choice and is not visible to the protocol.

### Native clients

Native apps are public clients: they have no client secret. Every compatible instance must accept these client identifiers with exactly these redirect URIs:

| Client identifier | App | Redirect URI |
| --- | --- | --- |
| `discophile-desktop` | Discophile for computers | `http://127.0.0.1:{port}/connect/callback`, where `{port}` is any port from 1024 to 65535 |
| `discophile-android` | Discophile for Android | `it.discophile.android:/connect/callback` |
| `discophile-ios` | Discophile for iPhone | `it.debba.discophile:/connect/callback` |

For the loopback redirect, the server must accept any port in the range and compare the rest of the URI exactly ([RFC 8252, section 7.3](https://www.rfc-editor.org/rfc/rfc8252#section-7.3)). It must not accept `localhost` or other hosts for `discophile-desktop`.

Instances may support further clients. They must never require a client to obtain a secret, signature, or license from the official service.

### Authorization request

The client generates, for each attempt and with a cryptographically secure random generator:

- `code_verifier`: 32 random bytes, base64url-encoded without padding (43 characters).
- `state`: 32 random bytes, base64url-encoded without padding.

It then opens the authorization endpoint with these query parameters:

| Parameter | Value |
| --- | --- |
| `response_type` | `code` |
| `client_id` | A native client identifier. |
| `redirect_uri` | The client's redirect URI. |
| `scope` | `account:read offline_access` |
| `state` | The random state. |
| `code_challenge` | `base64url(SHA-256(code_verifier))` without padding. |
| `code_challenge_method` | `S256` |
| `resource` | The `resources.api` value from discovery ([RFC 8707](https://www.rfc-editor.org/rfc/rfc8707)). |

Example:

```text
https://connect.discophile.app/oauth/authorize?response_type=code&client_id=discophile-desktop&redirect_uri=http%3A%2F%2F127.0.0.1%3A53682%2Fconnect%2Fcallback&scope=account%3Aread%20offline_access&state=Ys0X3s2b6n6q4TQm7bH2b8m3oUq1i8T0yS0pWm2bJXc&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&code_challenge_method=S256&resource=https%3A%2F%2Fconnect.discophile.app%2Fapi%2Fv1
```

The server must:

- Reject unknown clients and redirect URIs without redirecting, showing an error page instead.
- Require `code_challenge_method=S256` and a challenge of 43 base64url characters.
- Reject unknown scopes, and scopes the client may not request, with `invalid_scope`.
- Reject a `resource` other than its own resources with `invalid_target`.
- Show the person which app is asking, which instance they are signing in to, and what the app will be able to read, and let them allow or deny.

The person's decision returns to the redirect URI with `code` and `state`, or with `error` (for example `access_denied`) and `state`. Error parameters follow [RFC 6749, section 4.1.2.1](https://www.rfc-editor.org/rfc/rfc6749#section-4.1.2.1). The server should include `iss` ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)); when present, the client must compare it with the issuer and abandon the attempt if it differs. The callback query is `application/x-www-form-urlencoded`, so `+` stands for a space.

The client must accept exactly one callback whose `state` matches the attempt, reject repeated parameters, and abandon the attempt after five minutes. A desktop loopback listener must bind only to `127.0.0.1`, answer only `GET /connect/callback` with the exact `Host` header, and return a page that contains no request values.

### Token request

`POST /oauth/token` with `Content-Type: application/x-www-form-urlencoded`:

| Parameter | Value |
| --- | --- |
| `grant_type` | `authorization_code` |
| `code` | The received code. |
| `redirect_uri` | The same redirect URI. |
| `client_id` | The same client. |
| `code_verifier` | The verifier. |
| `resource` | Optional. When present, it must equal the resource of the authorization request. |

Successful response:

```json
{
  "access_token": "dca_3f6Yb1yQyT0Qv0u1oJqvH2wqf6wQ8tXg",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "dcr_xQ2h8mW2z7m0rS4yU6cQ1aB9kP3nE5tL",
  "scope": "account:read offline_access"
}
```

Tokens are opaque. Clients must not parse them or depend on their length or prefix, and must store them only in the platform's keychain or an equivalent protected store.

Authorization codes are single use and expire within 60 seconds. If a code is presented twice, the server must reject it and revoke every token issued from it.

### Refresh

`POST /oauth/token` with `grant_type=refresh_token`, `refresh_token`, `client_id`, and optionally `resource`. The response has the same shape and always contains a new refresh token. The previous refresh token stops working.

If a refresh token that was already replaced is presented again, the server must treat the delegation as compromised and revoke it entirely. A client that loses a refresh response, for example to a network failure after the server answered, will therefore have to sign in again; servers may accept the previous refresh token for a few seconds to soften this, but are not required to. A client must therefore refresh at most once at a time and persist the new tokens before using them.

Clients should refresh when the access token expires within 60 seconds, and may refresh once when the API answers `401` before an access token's expiry. A failed refresh with `invalid_grant` means the delegation ended: the client clears its tokens and asks the person to sign in again. Network errors, `5xx` responses, and other errors keep the tokens for a later attempt. A refresh response without a new refresh token is invalid: the client never presents the previous refresh token again, because that would revoke the delegation.

### Lifetimes

| Item | Lifetime |
| --- | --- |
| Authorization code | 60 seconds, single use |
| Access token | 3600 seconds |
| Refresh token | 30 days since it was issued; each refresh issues a new one |

Instances may choose shorter lifetimes and must state them in `expires_in`. Clients must work with any positive value.

### Revocation

`POST /oauth/revoke` ([RFC 7009](https://www.rfc-editor.org/rfc/rfc7009)) with `token` and `client_id`, and optionally `token_type_hint`. Revoking either token of a delegation ends the whole delegation: its access and refresh tokens stop working on every server node immediately, including access tokens that have not expired. The server answers `200` even for unknown tokens.

When the person signs out or changes instance, clients delete their local tokens and revoke the refresh token. Local deletion never depends on the outcome of the revocation request; clients should tell the person when revocation could not be confirmed. The person can also revoke a delegation from the instance's dashboard; clients notice through `401` responses.

### OAuth errors

Token and revocation errors use [RFC 6749, section 5.2](https://www.rfc-editor.org/rfc/rfc6749#section-5.2):

```json
{ "error": "invalid_grant", "error_description": "The authorization code is invalid or has expired." }
```

Version 1 uses `invalid_request`, `invalid_client`, `invalid_grant`, `unauthorized_client`, `unsupported_grant_type`, `invalid_scope`, `invalid_target`, `access_denied`, `temporarily_unavailable`, and `server_error`. A `429` response may carry `Retry-After`.

## Account

`GET /api/v1/account` requires `Authorization: Bearer <access token>` with the `account:read` scope and the `resources.api` audience.

```json
{
  "instanceId": "9b0d0c5e-7f1e-4c39-9d0e-2f3a2c1b5e77",
  "account": {
    "id": "u_6sQb2kL8wN4tR1",
    "name": "Ada Example",
    "email": "ada@example.com",
    "emailVerified": true
  },
  "plan": {
    "tier": "connect",
    "name": "Connect",
    "source": "manual",
    "expiresAt": "2027-01-31T00:00:00Z",
    "entitlements": [
      { "id": "devices.paired", "limit": 10, "available": false },
      { "id": "sync.connections", "available": false },
      { "id": "sync.preferences", "available": false },
      { "id": "backup.configuration", "available": false },
      { "id": "playback.remote", "available": false },
      { "id": "playback.handoff", "available": false }
    ]
  }
}
```

| Member | Meaning |
| --- | --- |
| `instanceId` | Equals `instance.id` from discovery. Clients reject a mismatch. |
| `account.id` | A stable, opaque identifier of at most 128 characters, unique within the instance. |
| `account.name` | A display name, possibly empty. |
| `account.email` | The account's email address, or `null`. It is not a global identifier and may change. |
| `account.emailVerified` | Whether the instance verified the address. |
| `account.avatarUrl` | Optional selected profile picture URL, or `null` for initials. Existing clients may ignore it. |
| `plan.tier` | The effective tier identifier, already accounting for expiry. |
| `plan.name` | An English display name for tiers the client does not know. |
| `plan.source` | How the tier was obtained: `default`, `manual`, or values added later. Clients show unknown values generically. |
| `plan.expiresAt` | When the current tier ends, or `null`. |
| `plan.entitlements` | The benefits of the tier, described below. |

### Profile pictures

`account.avatarUrl` is optional. Clients keep initials when it is missing, invalid or unavailable.
The URL must be HTTPS, except for a development URL on the instance's own loopback origin.
Clients send the account bearer token only to the instance's own origin, never to an external
picture provider, and do not follow image redirects. Pictures should be bounded before decoding.

The official instance returns the selected Google/GitHub URL directly. For an uploaded picture it
returns `/api/v1/account/avatar?v=<version>` as an absolute URL. This endpoint requires a current
bearer token with `account:read`, returns only that account's selected upload, and uses `no-store`.
It never accepts another account's identifier. Browser-only `/avatar/<id>` addresses remain private
to browser sessions and are not used by native clients. A change appears after refreshing the account.

### Account namespace

Clients read the account right after the token exchange to learn `account.id`; if that fails, they may revoke the new tokens rather than keep them without an account. Clients identify local data that belongs to a Connect account by the pair of the instance's canonical origin and `account.id`. An email address alone is never sufficient. Changing instance requires a new sign-in; tokens, identifiers, and any synchronized data are never sent to the new instance automatically. Moving data between instances is a separate, explicit operation.

### Tiers

Version 1 defines these identifiers. Instances may define others and may grant any tier without payment.

| Tier | Meaning |
| --- | --- |
| `free` | The default. Standalone use and direct connections to the person's own servers need no Connect account and have no Connect limits. |
| `connect` | Connect cloud services as they become available. |
| `supporter` | The Connect benefits with a larger contribution to development. |

When a temporary tier expires, the effective tier returns to `free` unless another entitlement applies. Expiry must take effect when it is reached, without depending on a scheduled job.

### Entitlements

An entitlement is a benefit included in the person's tier:

- `id`: a dotted identifier.
- `limit`: an optional positive integer, such as a number of devices.
- `available`: whether this instance offers the benefit now. For a benefit that needs a capability, it is `true` only when the instance advertises that capability.

Clients must not enable a feature because an entitlement is present: they also need the capability in discovery and a client version that implements it. Clients should present entitlements with `available: false` as planned, not as working. They must ignore identifiers they do not know.

Version 1 defines:

| Identifier | Benefit | Capability required |
| --- | --- | --- |
| `devices.paired` | Paired playback devices, with `limit` | `devices` |
| `sync.connections` | Encrypted synchronization of library connections | `sync` |
| `sync.preferences` | Encrypted synchronization of chosen preferences | `sync` |
| `backup.configuration` | Encrypted configuration backups | `backup` |
| `playback.remote` | Remote control | `remote` |
| `playback.handoff` | Playback handoff between devices | `handoff` |
| `supporter.recognition` | Optional public recognition | none |
| `previews` | Access to previews when they exist | none |

Data export, data deletion, and access revocation never require a tier.

## API errors

Errors from `/api/v1` have this shape:

```json
{ "error": "invalid_token", "message": "The access token is missing, expired, or revoked." }
```

| Status | `error` | When |
| --- | --- | --- |
| 400 | `invalid_request` | Malformed request. |
| 401 | `invalid_token` | Missing, expired, or revoked token, or the wrong audience. The response carries `WWW-Authenticate: Bearer error="invalid_token"`. |
| 403 | `insufficient_scope` | The token lacks the scope. `WWW-Authenticate` names the required scope. |
| 404 | `not_found` | Unknown endpoint, including endpoints of capabilities the instance does not offer. |
| 429 | `rate_limited` | Too many requests; `Retry-After` gives seconds. |
| 5xx | `server_error` or `temporarily_unavailable` | Server problems. Clients keep their tokens. |

`message` is English text for logs and developers. Clients show their own localized text.

## Security considerations

- The protocol is public; its security relies on TLS, PKCE, exact redirect URIs, short-lived opaque access tokens, rotating refresh tokens, and the person's consent.
- Servers must check, on every request, that the token's delegation is still valid and that the account still exists. Signature validity alone is not sufficient, so that revocation takes effect immediately on every node.
- Servers store tokens and codes only as one-way hashes.
- Version 1 carries no library credentials, provider configurations, or playback data. Those will be end-to-end encrypted on devices under a separate specification, and an instance's account access will not be enough to decrypt them.
- A malicious or compromised instance can still deny service or lie about plans. Clients treat plans as informational and never as a reason to restrict local playback or direct connections to the person's own servers.

## Versioning

The path prefix `/api/v1` and the `protocolVersions` value identify this version. Additions that old clients can ignore, such as new members, capabilities, entitlements, tiers, or plan sources, do not change the version. Incompatible changes use a new version, and instances may serve several versions side by side.

## Conformance

The [conformance script](conformance/check.mjs) checks the public behavior of an instance: discovery, origin binding, OAuth metadata, PKCE and redirect URI enforcement, and API error formats. It needs no account and does not modify data:

```sh
node conformance/check.mjs https://connect.example.org
```

Sign-in, refresh, and revocation require a person to sign in. Test them with Discophile for computers configured for the instance, or follow the [examples](examples.md).

## Optional native services extension

The [services specification](services.md) defines capability version 1 for devices, sync, backup, remote and handoff. Native clients may request the additional connect:manage scope when advertised; existing account-only clients keep their current scope and behavior. Prices and availability are read from the instance catalog, not inferred from a tier name.
